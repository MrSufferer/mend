# x402 evidence and provider recovery authority

Research for [Establish x402 evidence and provider recovery authority](https://github.com/MrSufferer/mend/issues/38), inspected 2026-10-16. This is an investigation, not an approved integration design. Mend baseline: `6dffd35985787bf51acc2307516c1190a2d12b9c`. Upstream links below describe moving `main`; pin the selected SDK/spec version before implementation.

## Finding

A provider integration is necessary. A payment receipt alone cannot establish which business operation finished, recover its private output, authorize another execution, or grant Mend access to the merchant's funds. The current Mend implementation supplies those capabilities through its own database, conversion service and separately authorized refund reserve; they are not inherited by pointing it at another x402 URL. See the [existing purchase flow](../x402-purchases.md), [conversion authority](../../backend/conversion.ts), and [registrar](../../backend/registrar.ts).

## Protocol facts

- Core v2 describes payment requirements, selected payment data, settlement responses, and facilitator `/verify`, `/settle`, `/supported`. Requirements identify scheme, CAIP-2 network, asset, atomic amount and recipient. Verification is read-only; settlement commits payment state. A resource URL is metadata, not a durable application job record. `maxTimeoutSeconds` is a payment-completion limit, not Mend's purchased delivery deadline. [Core specification](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md).
- The current spec distinguishes `authorization` (verify, execute, settle), `upfront` (settle, execute), and `escrow` (commit deposit, execute, final charge). Support is mechanism-specific. Therefore neither “all x402 requests settle before work” nor “all requests escrow funds” is correct. Facilitator `/supported` is a compatibility input, not proof of provider recovery capability. [Core specification](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md).
- For `exact`, authorization is the default; upfront execution failure can leave payment committed, and the scheme explicitly provides no refund remedy. A lost response after settlement remains possible even if normal handler failures are not charged. Escrow availability elsewhere does not retrofit refunds onto an ordinary exact transfer. [Exact scheme](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact.md).
- EVM exact has multiple asset-transfer methods. EIP-3009 authorizes a one-time transfer with payer, recipient, value, validity window and nonce; these fields do not sign an HTTP body or a purchased service policy. Permit2 and ERC-7710 have different authorization prerequisites. An uncertain broadcast may return `settlement_pending` and its transaction hash for reconciliation. Do not extrapolate Mend's EOA/nonce checks to every mechanism. [EVM exact](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_evm.md).
- The optional `payment-identifier` extension supplies a reusable client id. Its specification describes cached replay for matching payloads, conflict for mismatches, and binding to a normalized fingerprint scoped by merchant/tenant/route. Resource-server deduplication and facilitator deduplication are separate responsibilities. Merely echoing an id does not implement durable execution fencing, output retention, or crash recovery. [Identifier extension](https://github.com/x402-foundation/x402/blob/main/specs/extensions/payment_identifier.md).

Context7 was consulted with one library resolution and two documentation queries. Its FAQ excerpt described escrow as future work, while current core specifications already describe mechanism-specific escrow. This note uses the more specific current specifications; a target provider's actual deployed version remains to be established.

## Capability and evidence matrix

The rightmost column contains proposed requirements inferred from protocol boundaries and Mend's existing controls; it is not a protocol guarantee or a human-approved policy.

| Capability / failure | What Mend has today | Evidence and authority needed from another provider |
| --- | --- | --- |
| Bind purchase to operation | One private submission/order, snapshotted terms, one stored payment authorization. [Orders](../../lib/server/orders.ts), [schema](../../lib/server/schema.ts) | Authenticated provider + endpoint identity; provider operation id; immutable input/request fingerprint; original terms/version; binding to payment and authorized customer. An arbitrary receipt or order id is insufficient. |
| Lost payment response / uncertain settlement | Persist original authorization before settlement; reconcile receipt/nonce; no replacement signature. [Payments](../../lib/server/payments.ts), [receipt checks](../../lib/server/payment-receipts.ts) | Durable payment reference and network-specific confirmation evidence, including pending state and reconciliation method. Timeout must not imply unpaid, failed, or refund-eligible. |
| Lost synchronous response | Mend instead persists PDF results for authenticated retrieval. [Conversion](../../backend/conversion.ts) | Provider must retain the exact response or a recoverable output reference and expose authenticated retrieval without another paid execution. If its cache expired, recovery may be impossible; fresh recomputation is a different action. |
| Asynchronous job | Durable execution generations and private output publication. [Conversion](../../backend/conversion.ts) | Submission acknowledgement bound to job id; authenticated status/history; output digest/type/expiry; delivery access. An HTTP success accepting a job is not proof that the eventual result exists. |
| Restore access | Fresh output verification and controlled publication. [Conversion](../../backend/conversion.ts) | Authorized access restoration/response replay with ownership and expiry checks. Distinguish output prepared, made available, and actually retrieved. Missing access is not necessarily missing output. |
| Retry without duplicate work | Trusted worker requires stopped execution, final absence, policy allowance, original deadline and atomic generation claim. [Agent](../../backend/agent.ts), [conversion](../../backend/conversion.ts) | Durable idempotency and provider-enforced generation/fencing; evidence that earlier execution cannot still publish or cause side effects. Unknown execution means observe/escalate. A facilitator's duplicate-payment protection does not protect business side effects. |
| Refund eligibility | Independent registrar verifies payment, worker evidence and purchased policy before fencing disposition. [Registrar](../../backend/registrar.ts) | Merchant-approved policy and independently verifiable evidence; atomic exclusion of incompatible delivery/refund actions. Specify partial fulfillment and expiry explicitly. Deadline passage alone is insufficient. |
| Refund transfer | Isolated registration and execution; canonical receipt verification; reserve capacity can block completion. [Authority ADR](../adr/0001-isolate-refund-authority.md), [refund service](../../backend/refund.ts), [chain checks](../../backend/refund-chain.ts) | Explicit merchant authorization, funded source on supported network, bounded signing service/contract, original payer/asset/amount binding, idempotent submission and receipt reconciliation. A request or entitlement is not confirmed repayment. |

## Proposed minimum integration seam

A candidate adapter should declare capabilities rather than pretend every provider supports every recovery action:

1. **Enroll a trusted provider binding:** approved origin/endpoint identifiers, accepted scheme/network/token/transfer-method combinations, evidence authentication, and scoped credentials. Bind the merchant recipient to that enrollment; do not trust a customer-supplied URL or payer string as authority.
2. **Record one purchased obligation:** provider operation id, request fingerprint, payment reference, authenticated customer, and immutable purchased terms (delivery, retention, retries, refund exclusions). Support structured JSON responses as well as stored files; keep PDF upload fields within the PDF adapter.
3. **Observe canonical state:** payment, execution, output, delivery and refund remain separate dimensions. Evidence needs issuer, operation, revision/time and provenance. Missing or stale evidence remains unknown. Provider attestations require an explicit trust decision; do not present them as independent on-chain proof of execution.
4. **Invoke only declared actions:** replay/restore, bounded retry, or refund request with a stable action id and expected revision. The provider must enforce the action's preconditions atomically; model prose cannot confer authority. Document how an interrupted action is reconciled.
5. **Return an auditable outcome:** no second charge for restoration; no duplicate execution for retry; actual matching transfer proof for refund. Unsupported actions must remain explicit and escalate, rather than be simulated.

This preserves the separation already enforced by Mend's [agent tools](../../backend/agent.ts) and [refund authority](../adr/0001-isolate-refund-authority.md), while moving provider-specific evidence and actions behind a boundary. It does not decide whether the first integration must support all three remedies.

## Compatibility and unresolved decisions

Current code hard-codes exact EOA ERC-3009, Arc testnet `eip155:5042002`, one configured merchant, 1 test USDC, six-decimal token amounts, and an Arc-specific receipt reader. Schema also contains required upload/pages fields and singleton merchant controls. See [payments](../../lib/server/payments.ts), [schema](../../lib/server/schema.ts), [purchase documentation](../x402-purchases.md). External support requires explicit compatibility work; provider listing in an x402 directory does not establish Arc support, refund authority, or customer adoption.

Before selecting the external proof case, establish its deployed protocol/SDK version; mechanism, chain and token; synchronous versus asynchronous semantics; durable response retention; evidence APIs; idempotency across restarts; permitted remedies; and who funds/signs refunds. The separate provider investigation must verify these facts. A non-Arc provider might be supported by a separate adapter while PDF stays on Arc; whether that scope is acceptable remains a product decision.

No provider was contacted, no accounts created, no paid endpoint invoked, and no funds moved. Findings are documentation/source inspection, not live interoperability certification. The initial Context7 attempt was blocked by an automatic-review usage limit; the user resumed the session and all three prescribed Context7 commands then succeeded.
